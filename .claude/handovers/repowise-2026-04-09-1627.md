## Key Findings This Session

### Repowise vs ChunkHound/Codeindex — Verdict
- **Repowise generates LLM prose descriptions** of code, not structural indexes
- For a solo dev with codeindex + ChunkHound, repowise is **redundant overhead**:
  - 6+ min GPU time per small repo (claude-pulse: 13 pages in 6 min)
  - LLM hallucinations in output (qwen3 leaked Chinese text `:冷启动` in docs)
  - Semantic search is over generated prose, not actual code
- **ChunkHound already provides** semantic search over real code chunks — faster, more accurate, no LLM cost
- **Where repowise has value**: team onboarding wikis, MCP server for AI context, dashboards for team repos
- **Idea**: build a wiki export from ChunkHound's DB — gets the useful parts without the overhead

### Gemini API — Worth Exploring Further
- Free tier is very generous: 1,500 req/min for embeddings
- `gemini-embedding-001`: 768-dim vectors, free, fast, good quality
- API key: set up and working (`GEMINI_API_KEY` in zsh_alias.sh)
- **User wants to explore Gemini API more broadly** — beyond just embeddings
- Could be useful for: cheap/free LLM calls, embeddings in ChunkHound, other tooling

### Pipeline Architecture (for reference)
- **Embedder options**: gemini (free), openai ($0.02/1M tokens), mock (testing)
- **Vector store options**: InMemoryVectorStore (no persistence), LanceDBVectorStore (local files, persists), PgVectorStore (Postgres)
- `--resume` only works with persistent stores (LanceDB/PgVector)
- CLI search/export reads from SQLite (`wiki.db`), not LanceDB
- Web UI (`repowise serve`) reads from SQLite — needs init to complete Phase 4 (Persistence)

### Ollama Concurrency
- Ollama serves requests sequentially (one GPU, one model, one request at a time)
- Multiple `rwi` runs will queue, not parallel — let one finish before starting another
